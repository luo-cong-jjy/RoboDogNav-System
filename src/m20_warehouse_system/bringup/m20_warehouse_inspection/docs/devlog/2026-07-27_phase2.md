# 阶段 2 开发记录：官方 M20 与 F1 SCAN 导航闭环

日期：2026-07-27  
范围：官方模型、F1 local sensing、静态全局路线、SCAN 局部规划、闭环控制、安全门控、
RViz 运动学后端  
不在本阶段：运行时楼层切换、真实电梯、Gazebo 传感器/动力学、M20 SDK

## 1. 阶段目标与边界

本阶段在阶段 1 的平面双区域地图上，只启用 F1 做导航。F2 仍可在 RViz 总览中显示，
但不得进入 local sensing 或规划器。所有算法输出必须先经过安全层，任何仿真或实机
后端都不能直接订阅 SCAN 原始速度。

验收目标：

1. 能在 RViz 中显示可追溯到云深处官方仓库的 M20 模型。
2. 使用 active F1 点云生成局部雷达数据。
3. 从 F1 起点导航到含障碍目标并停车。
4. 证明全局路线、SCAN 局部轨迹和碰撞保护共同工作。
5. 证明持续非零输入下急停仍会立即把后端速度置零。
6. 新增包保持隔离，不修改当前 `src/third_party/SCAN-Planner` 和
   `src/m20_scan_planner` 的工作树。

## 2. 工作区审计与采用方案

### 2.1 官方 M20 资产

采用 `DeepRoboticsLab/deep_robotics_model` 固定 revision
`6113c62da96295e8d53abbc079af5296bf4649f8`。官方 M20 资产包含 17 个 link、16 个
joint 和 17 个 STL。

处理方式：

- `urdf/vendor/M20.urdf` 与 `meshes/*.STL` 保存官方字节副本。
- `urdf/m20_official.urdf` 只处理非 URDF MuJoCo 块和 ROS package URI。
- `xacro/m20.urdf.xacro` 单独增加 `lidar_link` 和 `imu_link`。
- 不修改官方质量、惯性、关节与 mesh。

### 2.2 SCAN 算法隔离

从 Apache-2.0 的 SCAN-Planner 和当前工作区已验证的 M20 适配中提取必要源码，放入
新包 `m20_scan_navigation`。复制文件保留 Apache 声明并在 `NOTICE` 记录来源。
原第三方目录没有被修改。

### 2.3 平面导航分层

最终采用：

```text
active F1 occupancy
  -> 0.60 m 膨胀 A*
  -> 0.90 m 间距短子目标
  -> SCAN GridMap / Dynamic A* / B-spline
  -> closed-loop cmd_vel_raw
  -> collision guard + safety supervisor
  -> cmd_vel_safe
  -> RViz kinematic backend
```

静态 A* 负责全局连通性和障碍走廊；SCAN 负责局部占据、动态重规划和光滑轨迹。独立
collision guard 不信任任何单一规划器，会对原始导航指令做 1.0 s 前视。

## 3. 新增模块

### 3.1 `m20_official_description`

- 官方 M20 URDF/mesh 可追溯包装。
- 项目传感器 xacro wrapper。
- `robot_state_publisher` 与独立模型 RViz 启动。
- 资产数量、URI、vendor 副本哈希和 xacro 展开测试。

### 3.2 `m20_warehouse_sim`

- 50 Hz 二维刚体积分。
- 唯一输入 `/m20/control/cmd_vel_safe`。
- 输出 `/m20/sim/body_pose`、`/m20/sim/path`、`/joint_states`、
  `map -> base_link` 和 backend ready。
- 仿真初始位姿 `(-42.0, 0.0, 0.59)`，位于 F1。

该节点不模拟动力学、接触或真实 M20 执行机构；后续 Gazebo/实机只替换后端，不改变
上游安全接口。

### 3.3 `m20_scan_navigation`

- 隔离的 SCAN FSM、planner manager 与闭环 controller。
- F1 local sensing 配置只订阅 `/m20/map/active_global_cloud`。
- controller 只发布 `/m20/navigation/cmd_vel_raw`。
- 二维栅格 A*：占据阈值、圆形膨胀、八邻域且禁止对角穿角、折线简化和等距加密。
- 路线适配器：外部 goal -> 全局显示 route -> 顺序内部 `scan_goal`。
- 普通子目标接受半径 0.30 m；最终目标接受半径 0.15 m。
- SCAN 距目标 0.20 m 内不再尝试生成新轨迹，而是发布驻车轨迹并进入
  `WAIT_TARGET`。

### 3.4 `m20_inspection_core`

安全 supervisor：

- 导航/手动命令仲裁、限速、加速度限制和 0.5 s 命令超时。
- map ready、odom 新鲜度、floor switch hold、collision stop 和 e-stop 门控。
- 硬停止条件立即发布全零，不经过普通减速斜坡。
- 后端只能订阅 `cmd_vel_safe`。

collision guard：

- footprint 0.38 m，加安全余量 0.12 m，总保护半径 0.50 m。
- 对 active occupancy 膨胀并预测未来 1.0 s 位姿。
- 地图/odom 未就绪时 fail closed。
- 输出 transient-local `/m20/control/collision_stop` 和可诊断状态。

### 3.5 `m20_warehouse_inspection`

`f1_scan_rviz.launch.py` 组合：

- 双区域/active F1 map server；
- 官方模型与 `robot_state_publisher`；
- `map -> world` 显式静态 TF；
- RViz 运动学后端；
- safety supervisor 与 collision guard；
- local sensing、A* route adapter、SCAN planner/controller；
- 阶段 2 RViz 配置。

RViz 同时显示 F1/F2 总览，但 active cloud、local lidar 和规划路径都只来自 F1。

## 4. 集成迭代与问题记录

### 4.1 直接 SCAN 目标

先用 `navi_mode=1` 验证无障碍目标 `(-38, 0)`，机器人正确到达并停止。随后直接发送
`(-35, -10)`，直线全局参考穿过静态障碍。local sensing 能报告碰撞，但仅依赖局部
规划不足以保证该长距离静态路线。

结论：必须在 SCAN 前增加当前楼层静态全局连通规划。

### 4.2 整条 A* 路线输入 SCAN

增加膨胀栅格 A* 后，最初把整条 `nav_msgs/Path` 送入 `navi_mode=3`。A* 路线本身
无碰撞，但 SCAN 的全局多项式拟合在障碍拐角切角。新增的 collision guard 在实际进入
障碍前于约 `(-37.7, -6.17)` 断言停车，证明最后一道保护有效，也证明整条多项式方案
不能作为当前默认实现。

结论：全局路线不能只验证离散折线，还必须约束连续轨迹。

### 4.3 顺序短子目标

路线适配器改为每约 0.90 m 发送一个 SCAN 目标。这样每段 B 样条都局限在 A* 安全走廊
附近。F1 验收路线生成 16 个 pose、15 个内部子目标，总长 12.54 m。全程没有
collision guard 停车，也没有 local sensing 碰撞报告。

### 4.4 终点无限重规划

机器人到达最终目标附近后，FSM 位于 `REPLAN_TRAJ`。SCAN planner manager 对距离小于
0.20 m 的新规划返回 `Close to goal`，原 FSM 却继续以高频率重试。

修复：

- 增加可配置 `fsm.target_reached_tolerance=0.20`。
- `REPLAN_TRAJ` 中先判断二维目标距离。
- 达到阈值后发布以当前 odom 为目标的驻车 B 样条。
- 清除当前目标和失败计数并转入 `WAIT_TARGET`。
- 路线适配器使用独立的 0.15 m 最终接受半径，且保持 `GOAL_REACHED`，不再被后续
  odom 覆盖为 `READY`。

修复后相同路线只规划 15 条运动轨迹和 1 条驻车轨迹，稳定停在目标 0.20 m 范围内，
无重复重规划。

## 6. 运行验收结果

### 6.1 完整 F1 路线

输入：

```text
start = (-42.0, 0.0)
goal  = (-35.0, -10.0)
```

结果：

```text
A* route             16 poses / 12.54 m
sequential SCAN goals 15
route state           GOAL_REACHED
stable sampled pose   (-35.0486, -9.8302, 0.59)
goal position error   0.177 m
safe velocity         (0, 0, 0)
safety state          NAVIGATION
collision guard       CLEAR
SCAN FSM              WAIT_TARGET
```

该稳定采样误差小于 SCAN 0.20 m 完成阈值。运行中未出现碰撞停车。

### 6.2 急停

在手动输入持续发布 `linear.x=0.20 m/s` 时：

```text
before e-stop: cmd_vel_safe.linear.x = 0.20
after e-stop:  cmd_vel_safe = all zero
safety state:  E_STOP
```

释放急停后状态恢复 `NAVIGATION`。这项测试验证的是持续非零输入下的硬门控，而不是
仅在机器人原本静止时检查状态字符串。

### 6.3 RViz 与 QoS

- WSL 桌面显示下 RViz 正常创建 OpenGL 4.2 窗口并加载阶段 2 配置。
- RViz local cloud、SCAN cloud subscriber 和 local sensing publisher 的最终实时端点
  都是 `BEST_EFFORT / VOLATILE`。
- 纯 `QT_QPA_PLATFORM=offscreen` 模式因 Ogre GLX 不支持无父窗口而失败；桌面显示
  模式成功，因此该错误不属于项目配置故障。

## 7. 已知非阻塞现象

- 官方 M20 的 `base_link` 自带惯性。KDL 会提示根 link 惯性不受支持，但
  `robot_state_publisher` 仍加载全部模型。为保持官方树不被篡改，本阶段不增加 dummy
  root；Gazebo 阶段可在 profile wrapper 中处理。
- 用户 Ctrl-C 时，第三方 `pcl_render_node` 与 ROS 静态 TF 进程可能由 launch 报
  `exit code -2`；其余项目节点均正常退出。这是 SIGINT 退出显示，不是运行中崩溃。
- 阶段 2 route state 仍是字符串诊断。带目标 ID、floor ID 和 map generation 的 typed
  Action 在阶段 3/4 实现。

## 8. 实机迁移约束

- 保持 `cmd_vel_raw -> safety -> cmd_vel_safe -> backend` 不变。
- 实机 M20 SDK adapter 只能替换 RViz kinematic backend。
- `body_pose` 由真实定位/融合 odom 替换，坐标语义保持一致。
- `local_cloud` 由真实雷达预处理替换，QoS 和 frame 必须显式验证。
- 仿真地图偏移只能存在于 profile transform，任务不能通过 x 坐标推断楼层。
- 实机上线前必须增加硬件急停、通信失效、定位质量和手动控制碰撞保护。

## 9. 下一阶段入口

阶段 3 从现有静态 active F1 基线开始，实现完整的楼层切换事务：

1. 断言 floor-switch hold 并确认安全速度为零。
2. cancel 当前导航并使旧轨迹失效。
3. 用 generation 原子切换 active PCD/occupancy。
4. 清空并确认 local sensing 与 SCAN GridMap。
5. 有确认地把仿真位姿传送到目标楼层电梯出口。
6. 新地图、位姿、TF 和局部点云全部 ready 后释放 hold。
7. 任一步失败都保持旧地图或进入 `FAULT_HOLD`，不允许带故障继续运动。
