# 阶段 3 开发记录：双向地图热切换与导航重置事务

日期：2026-07-27  
版本：0.4.0  
范围：typed interfaces、active PCD/occupancy 切换、generation-aware local sensing、
SCAN reset、仿真位姿传送、双向 floor-switch Action、安全保持  
不在本阶段：自动巡检任务、真实电梯、Gazebo 雷达/动力学、实机定位与 M20 SDK

## 1. 阶段目标

在阶段 2 的单层 SCAN 闭环上实现可靠的 F1↔F2 切换。F1 和 F2 仍是同一 `z=0` 平面
中的两块隔离区域，不建立可导航连接。跨区只能执行以下受控事务：

```text
到达电梯触发点
  -> 获取安全 hold 并确认停车
  -> 清空旧导航
  -> 切换 active PCD/occupancy
  -> 平面传送仿真位姿
  -> 清空新导航
  -> 确认新 generation 局部感知持续刷新
  -> 释放 hold
```

验收要求：

1. F1→F2 与 F2→F1 均可执行。
2. 切换期间后端只能收到零速度。
3. 旧事务不能覆盖新 generation。
4. 新地图 ready 和新鲜 local cloud 就绪前不能恢复导航。
5. 切换后的局部点云不含旧区域残留。
6. 任一步失败或取消后保持安全 hold。
7. 新功能包可随项目包集合迁入独立工作空间。

## 2. 模块与接口

### 2.1 `m20_warehouse_interfaces`

新增不依赖业务实现的接口包：

```text
FloorState.msg
  floor_id + generation + ready + phase + message

LocalSensingState.msg
  floor/generation/readiness + 新鲜帧计数 + 点数 + XY 边界

SwitchMap.srv
  target_floor + expected_current_generation

ResetNavigation.srv
  floor_id + generation

SetSimulationPose.srv
  x + y + yaw + floor_id + generation

SwitchFloor.action
  source_floor + target_floor + elevator_id
  phase feedback
  typed success/error result
```

### 2.2 地图服务

`m20_flat_map_server` 启动时预加载所有 PCD 和 occupancy。`/m20/map/switch` 使用
compare-and-swap：只有请求的 `expected_current_generation` 等于当前代次才进入
LOADING。成功提交 cloud、occupancy、marker 和 floor state 后 generation 只递增一次。
原有 floor/generation/ready 拆分话题保留给旧观察工具，新事务使用
`/m20/map/state`。

### 2.3 generation-aware local sensing

新增 `m20_multifloor_map`，替代阶段 2 中只接受第一张 PCD 的第三方 renderer：

- `ready=false` 时立即清空全局缓存和 local cloud。
- 新 active cloud 必须绑定当前 `floor_id + generation`。
- 按机器人位姿裁剪局部窗口。
- 单帧最多 3500 点并轮转切片，连续帧覆盖完整局部集合。
- local cloud 使用 reliable/volatile，减小 DDS 大分片静默丢失概率。
- typed state 暴露新鲜帧、点数和 XY 范围，不需要订阅大点云即可诊断残留。

### 2.4 SCAN reset 与路线隔离

`/m20/navigation/reset` 在有 odom 时先发布驻车 B 样条，然后：

- 调用 `GridMap::resetBuffer()`。
- 清空活动 waypoint、目标、路线和失败状态。
- 清零局部/全局进度字段。
- 转入 `WAIT_TARGET`。

路线适配器订阅锁存的 floor hold。hold 期间立即清空短子目标、拒绝新 goal，避免平面
传送后继续追踪旧楼层路线。

### 2.5 仿真位姿传送

`/m20/sim/set_pose` 校验 x/y/yaw 为有限数值，原子设置平面位姿，清零当前 twist 与
缓存命令，重置历史路径并立即发布确认状态。该服务只属于 RViz 仿真 profile；实机
必须以定位地图切换和初值确认替代。

### 2.6 floor-switch Action

`m20_floor_switch_manager` 使用可重入 callback group 和四线程执行器。事务顺序：

```text
校验 source/target/elevator、active map 和触发位姿
  -> HOLDING
  -> 连续 3 次确认 cmd_vel_safe 与 odom 已停止
  -> RESETTING_OLD_NAV
  -> ELEVATOR_TRANSIT
  -> SWITCHING_MAP（generation CAS）
  -> RELOCATING
  -> RESETTING_NEW_NAV
  -> WAITING_SENSING（基准计数后新增 3 帧）
  -> COMPLETE 并释放 hold
```

F1→F2 的触发/释放为 `(-6.5, 0, 0)` → `(8, 0, π)`；反向计划由同一配置推导为
`(6.5, 0, π)` → `(-8, 0, 0)`。事务开始后的取消、超时、服务失败和异常均不释放 hold。

## 3. 集成问题与修正

### 3.1 Humble Action 执行协程

初版 Action execute callback 在 ROS 2 Humble 的执行线程中调用 `asyncio`，运行时出现
`no running event loop`；Humble logger 也不提供 Python 标准库的 `.exception()`。

修正为同步 execute callback，通过 `time.monotonic()` 控制超时，服务仍使用
`call_async()`；其他订阅和服务响应由 `MultiThreadedExecutor` 的剩余线程处理。异常
日志改用 `.error()`。修改后正反向 Action 均完成全部 feedback 阶段。

### 3.2 local cloud 的 DDS 传输

最初单帧包含约 6 万点且使用 best-effort，命令行新订阅者可能因 UDP 分片丢失而超时。
修正为：

- 每帧最多 3500 点。
- reliable/volatile 发布。
- 轮转起点，避免固定下采样永远遗漏同一批点。
- 在小型 typed state 中发布点数和边界，作为事务和验收的主要诊断面。

SCAN/RViz 的 best-effort reader 与 reliable writer 兼容。

### 3.3 旧点云残留判据

F1 全部位于负 X 区间，F2 全部位于正 X 区间。仅观察 RViz 颜色不足以证明缓存已清空，
因此 `LocalSensingState` 增加点数和 XY 边界。双向切换后通过边界符号直接证明没有
另一块区域残留。

## 6. 已知边界

- 官方 M20 `base_link` 自带惯性，KDL 仍会提示根 link 惯性不受支持。为保持官方模型
  字节和树结构，本阶段不改 vendor URDF；这不影响 RViz/TF/导航验收。
- 本阶段证明了单次正反向事务，不等同于 20 次稳定性验收。连续 20 次切换、内存趋势
  和恢复故障注入属于阶段 5 回归。
- Action 目前负责楼层切换，不负责自动把机器人导航到电梯。任务编排和 typed 导航
  gateway 属于阶段 4。
- `/m20/sim/set_pose` 不是实机能力；真实楼层切换必须等待定位质量、TF、雷达时间戳
  与新地图代次一致。

## 7. 下一阶段入口

阶段 4 在现有可靠事务上实现：

1. 带目标 ID、floor ID 和 generation 的导航 Action gateway。
2. typed mission step 和任务状态。
3. 自动执行 F1_A、F1_B、E1、F2_A、F2_B。
4. pause、resume、stop、restart、retry_current_step。

阶段 4 不修改 `cmd_vel_raw -> safety -> cmd_vel_safe -> backend` 安全出口，也不让任务
层直接操作 SCAN 内部状态。
